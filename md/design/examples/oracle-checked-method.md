# An oracle-checked method body

The external-method chapter explains why Sage produces a resolved call. This
chapter explains how the same `DbDropGuard::db` example checks that result
against rustc without teaching either emitter to imitate the other.

The fixture is a standalone Rust program under
`test-fixtures/oracle/mini_redis/db_drop_guard.rs`. The important body remains:

```rust
impl DbDropGuard {
    fn db(&self) -> Db {
        self.db.clone()
    }
}
```

## 1. Check Sage's semantic path

Exact equality is insufficient if both producers accidentally omit the same
body. A unit test using the same source program checks Sage's completed IR
directly:

```{anchor}
example_assert_elaborated_clone_body
```

This assertion establishes that body checking succeeded and that method syntax
was consumed. It then walks the semantic result: a statically dispatched
`Clone::clone` call receives a shared reference to the resolved `db` field,
whose base explicitly dereferences the local `self` binding.

This test establishes the checker and elaborator path, but it does not read the
oracle fixture or Sage's normalized output. The current comparison therefore
still lacks a fixture-specific assertion that `DbDropGuard::db` was emitted.
Both emitters could omit that method and nevertheless compare equal. The
general oracle coverage validator—or a focused assertion over this fixture's
Sage projection—remains required to close that gap.

## 2. Select the same source item independently

Source-written impl methods participate in the shared output. Sage discovers
them from checked impl items and excludes compiler-generated derive methods by
its own parse provenance:

```{anchor}
example_sage_source_impl_functions
```

The rustc emitter walks HIR impl items and independently applies the same
coverage boundary using rustc expansion provenance:

```{anchor}
example_oracle_source_impl_functions
```

Neither side uses the other side's item list. The exclusion is specifically for
derive-generated methods; source-written methods and methods generated by other
represented macros remain within the intended comparison scope.

## 3. Project into one shared typed tree

The two emitters begin from different internal representations:

- Sage already has a `ResolvedCall` with explicit dereference, field, and
  shared-reference nodes.
- rustc has a type-checked HIR method call plus method resolution and receiver
  adjustments in `TypeckResults`.

Each emitter minimally projects its native facts into `rust-ref`. For this body,
both must produce the same definition identities, static trait dispatch, types,
and explicit operations. The projection is per-emitter adaptation; there is no
comparison-side rewrite which can erase a disagreement.

## 4. Let deterministic text decide

The harness serializes the two `Crate<NormalizedDef>` values independently and
uses byte-for-byte equality as the conformance boundary:

```{anchor}
example_exact_oracle_comparison
```

If the strings differ, the JSON-tree comparison only explains where. It cannot
turn structurally equal but differently ordered output—or semantically unequal
output—into a pass.

The complete validation chain for this example is therefore:

```text
Rust fixture
├─ Sage parse/check/elaborate ── structural coverage assertion ── Sage projection
└─ rustc type checking ───────────────────────────────────────── rustc projection
                                                                    │
                                  deterministic serialized identity ┘
```

The semantic unit test catches regressions in Sage's elaborated body, while
exact comparison checks the output each emitter currently includes. It does not
yet fully establish the fixture's coverage boundary; that is the gap identified
above. The broader destination contract is specified in [Oracle Test
Harness](../oracle-test-harness.md).
